# Doc2md 第二轮偏差归纳与根因分析

- 文档编号：QA-D2M-2026-10-23-R2-ANA
- 输入：`docs/qa/round2/test-plan.md`（80 例，13 失败）、`docs/qa/round2/comparison.md`
- 被测版本：2.15.0
- 分析日期：2026-10-23

## 1. 结论先行

13 项偏差不是 13 个孤立缺陷，而是沿同一条链路的四类能力缺口：

1. **解析层**把「文件结构」压成「行序列」时丢失了位置与嵌套语义：段内分页符只能落到段尾（D6），嵌套表没有进入降维计数（D5）。
2. **映射层**用单特征/文本模式推断块类型：标题只看字号（D7），有序列表只看行首正则（D2 的列表分支），表格只把 `gridSpan`/`vMerge` 当降维（D5）。
3. **生成层**把 IR 文本直接当 Markdown 语法输出：没有字面量转义层（D2/D3 的主因），表格单元格只做朴素 `replace`（D4），md 直出失败被吞掉（D1），结果行仍报告已删除的 zip（D12）。
4. **校验/契约层**没有在边界上把「真实状态」变成可判定结果：同值 PATCH 仍递增 revision（D8），`limit=0` 三种语义（D9），配置解析异常逃逸成 E5000（D10），日志路径截断（D13），版本无单一来源（D11）。

其中 **D2/D3 是系统性风险**：只要下游把 Markdown 渲染成 HTML，源文档正文中的字面 `#`、`[]()`、`<script>` 就可能改变文档结构或进入可执行面。这不是「格式不好看」，而是转换契约的安全边界。

## 2. 解析层（S1）

### 2.1 分页符只按「段落」附加，不按「run 位置」切分

- 事实：`read_docx` 在整段处理完之后检查 `w:br type="page"`，然后把 `\x0c` 行追加到行序列（`doc2md/pipeline/s1_parse.py:1178-1182`）。
- 后果：段内分页时，分页前的文字与分页后的文字已被合成为一个 `Line`，S3 只能把 `page_break` 放在整段之后（D6）。
- 不足：解析器没有携带「段内偏移/run 序号」，S3 即使想切也没有依据；这属于**结构粒度缺失**，不是阈值问题。
- 影响：分页位置错位会改变阅读顺序与后续按页对齐的逻辑；对以「页」为审阅单位的场景影响更明显。

### 2.2 嵌套表的拍平没有进入降维账本

- 事实：`_docx_cell_text` 用 `tc.iter(w:p)` 把嵌套表的段落也拍平进单元格（`s1_parse.py:1033-1053`）；`_docx_table_rows` 的 `flat` 只统计 `gridSpan` 与 `vMerge`（`s1_parse.py:1070-1112`），嵌套表本身不计。
- 后果：外层表单元格出现 `内层A<br>内层B`，但 `meta.warnings` 为空、表块没有 `flattened_cells`（D5）。
- 不足：解析器没有「嵌套表」这一结构信号，也没有把「拍平事实」向上传递；docstring 承诺的 W1045 只覆盖了合并单元格，不覆盖嵌套表。
- 影响：数据降维被静默接受，审阅者无法从产物判断信息是否丢失。

### 2.3 表格单元格的 `<br>` 编码存在歧义

- 事实：O-05 用 `<br>` 表示单元格内段落边界；但源文本中本来就有字面 `<br>` 时，输出无法区分「源字面」与「结构换行」。
- 后果：`cell_br.docx` 中的字面 `<br>` 被下游当成换行；若源文本含 `<img>` 等标签，则直接成为原始 HTML（D3 的表格变体）。
- 不足：用 Markdown/HTML 语法字符充当内部结构标记，缺少转义或哨兵编码。
- 影响：表格内容可读性受损，且扩大了下游注入面。

### 2.4 解析层未保留「来源语义」

- DOCX 有 `w:numPr`（真实列表）、`w:pStyle`（Heading 样式）等显式语义，但当前列表/标题判定仍以文本模式与字号为主（D2 的列表误判、D7 的标题误判）。
- PDF 没有这些语义，只能靠几何/字体启发式；但 DOCX 场景本可以优先使用显式元数据，当前没有把「元数据优先、启发式兜底」的分层策略落到实处。
- 不足：解析产物 `Line` 只保留文本、字号、粗体等少量特征，缺少「是否带编号元数据」「是否在提示框/文本框」「段内 run 位置」等判别特征，导致后续只能猜。

## 3. 映射层（S3）

### 3.1 标题判定依赖单字号阈值

- 事实：N-8 的无编号分支为 `size >= base + 3.5`、长度 ≤60、无句末标点即升为 H2（`doc2md/pipeline/s3_structure.py:1044-1047`）。
- 后果：14pt 提示框文字（正文 10.5pt，+3.5）被升为 H2（D7）。这不是阈值调大一点就能解决：真实标题与提示框在字号上可能完全一致，区别在版面角色（框线、底色、居中、前后间距、是否独立成行）。
- 不足：判定器没有「版面角色」特征，也没有置信度/多信号投票；N-8 为了避免漏判把门槛降到与编号分支对齐，代价是假阳性。
- 影响：标题层级污染会进一步影响 TOC、分块与下游检索；属于结构语义错误。

### 3.2 列表判定只看行首模式

- 事实：`_ORDERED_ITEM` 用 `^\s*(\d{1,3})[、.．)）]\s*(?!\d)(?=\S)` 识别有序列表（`s3_structure.py:59`），`_is_ordered_item` 还会结合长度（`s3_structure.py:168-176`）。
- 后果：普通段落 `1. 这不是列表，而是以编号开头的正文段` 在 IR 中变成 `list_item`（D2 的列表分支）。
- 不足：DOCX 有 `w:numPr` 时本可确定「是不是列表」，但当前没有把该元数据作为强信号；PDF 侧也没有「悬挂缩进/编号对齐」等几何证据，只有文本正则。
- 影响：正文被错误列表化，Markdown 渲染后语义改变；与 S4 未转义叠加时，读者无法区分「源列表」与「碰巧以编号开头的正文」。

### 3.3 表格模型有损且降维不完整

- `_gfm_table` 只做 `strip`、`\n→<br>`、`|→\|`（`s3_structure.py:481-497`），没有处理反斜杠奇偶，导致 `\|` 变成 `\\|` 后列分隔符重新生效（D4）。
- 表格模型没有嵌套表、行/列跨度语义；`flattened_cells` 只来自 `row_flat`（`s3_structure.py:663-670`），嵌套表不入账（D5）。
- 不足：GFM 本身不支持合并/嵌套，降维是合理取舍；问题在于**降维没有完整账本**，且单元格转义没有按 Markdown 语法做闭包。
- 影响：复杂表格的列对齐与内容边界不可靠；审阅者不知道哪些信息被降维。

### 3.4 块级链接模型无法表达行内跨度

- 当前 `Block.links` 至多一条，S4 只渲染首条可渲染链接（`s4_render.py:120-141`）；行内多处链接会退化为纯文本或只保留一条。
- 这是已登记 O-11 的既定边界（ADR），本轮不作为新偏差；但它会放大 D2：字面 `[x](url)` 反而被渲染成链接，而真实的多链接段落却可能丢失链接。
- 不足：IR 的链接粒度与源文档的跨度粒度不一致；短期应在文档中明确「块级链接」能力边界，长期需要 span 级模型。

## 4. 生成层（S4 / CLI）

### 4.1 没有「字面文本 → Markdown」转义层

- 事实：`_inline` 只处理 `marks` 与 `links`，对正文不做任何转义（`s4_render.py:120-141`）；块级前缀（`#`、`>`、`-`、`1.`）直接由文本内容决定。
- 后果：字面 `#` 变标题、`>` 变引用、`[x](url)` 变链接、`**x**` 变粗体（D2）；原始 HTML 与 `javascript:` 字面量直通（D3）。
- 不足：IR 没有「这段文本是字面量还是已声明的 Markdown 语法」的标志位，S4 也没有统一的 `escape_literal()`。当前实现把「文本内容」与「Markdown 语法」混为一谈。
- 影响：文档语义可被源内容意外改变；下游渲染存在注入风险。这是本轮最高优先级的根因。

### 4.2 渲染红线过窄

- `assert_render_contract` 只检查 `](#`/`#page-` 与默认输出中的 `~~`（`s4_render.py:143-150`），不检查原始 HTML、行首块标记、表格列数、链接 scheme。
- 后果：D2/D3/D4 都能通过现有红线；测试套件全绿但语义已失真。
- 不足：把「渲染契约」缩减为两条字符串断言，缺少结构级校验（解析回读、列数、HTML 白名单）。

### 4.3 md 直出失败被吞掉

- 事实：`_apply_format` 捕获所有异常，打印 `md_emit_failed/E5031` 到 stderr 后返回空串（`doc2md/cli.py:505-526`）；`_report` 只看 `res["status"]`，`status=="ok"` 即返回 `EXIT_OK`（`cli.py:621-655`）。
- 后果：md 落盘失败（如目标名被目录占用）时 rc=0、stdout `status=ok`（D1）。这是**出口契约**错误：失败信息存在于 stderr，但机器调用方通常只看 rc/stdout。
- 不足：格式出口的失败没有回写到统一结果对象；「转换成功」与「指定格式落盘成功」被混为一谈。

### 4.4 结果行与真实产物不一致

- `--format md` 成功后删除 zip，但 `_report` 仍输出 `zip` 字段（D12）；结果行没有 `zip_removed`/`artifacts` 等能表达真实状态的字段。
- 不足：结果行是「输入转换结果」的投影，不是「本次所有产物」的事实清单；缺少产物状态机（written/removed/failed）。

### 4.5 管道转义是朴素替换

- `_gfm_table` 先 `.replace("\n","<br>")` 再 `.replace("|","\\|")`（`s3_structure.py:493-494`），没有先转义已有反斜杠，也没有处理字面 `<br>`。
- 后果：`\|` → `\\|`，反斜杠成为转义符后管道重新变成分隔符（D4）。
- 不足：缺少「按字符扫描、维护转义状态」的单元格编码器；用链式 `replace` 处理有状态语法，天然容易出错。

## 5. 校验/契约层

### 5.1 同值 PATCH 没有 no-op 判定

- 事实：`patch_block` 读取 `old_text` 后没有比较 `text == old_text`，直接 `UPDATE ... revision=revision+1` 并插入审计（`doc2md/edits.py:63-82`）。
- 后果：同值 PATCH 也递增 revision，后续重转被当成编辑冲突（D8）。
- 不足：编辑语义只有「写入」没有「无变化」；乐观锁把「版本变化」等同于「内容变化」。
- 影响：客户端重试/幂等提交会制造假冲突，阻塞正常重转。

### 5.2 `limit=0` 没有统一语义

- `/docs` 的 `_window` 把显式 0 当默认窗口（`api.py:234-247`）；`/jobs` 直接把 0 传给 SQL（`api.py:624-627`）；`/search` 把 0 传给检索（`api.py:837-843`）；CLI `docs list` 把 0 传给 `list_docs`，返回空集但 `total=1/has_more=true`。
- 后果：同一参数在四个出口有三种行为（D9）。
- 不足：分页语义没有在 API 边界统一，各端点各自解释；CLI 与 HTTP 没有共享同一套窗口解析器。

### 5.3 配置解析异常未映射为配置错误

- 事实：`create_app` 直接 `json.loads(override.read_text())`（`api.py:151-157`），未捕获 `JSONDecodeError`；CLI 顶层兜底把它归为 E5000/rc5。
- 后果：用户配置语法错误被报告为内部错误，无文件/行号（D10）。
- 不足：配置加载边界没有「用户输入错误 → E4001」的映射；异常分类依赖最外层兜底。

### 5.4 可观测性字段被截断

- 事实：`worker.py:413-415`、`419-426` 用 `str(job.get("path",""))[-64:]` 记录源路径。
- 后果：绝对路径从中间截断成 `lumes/fx/...`，无法定位（D13）。
- 不足：日志字段没有「完整路径/可定位标识」的契约；为了避免日志过长直接切片，牺牲了可诊断性。

### 5.5 版本与文档无单一来源

- README 首段仍写 v2.12.1（`README.md:3`），而 `pyproject.toml` 与 `doctor` 为 2.15.0（D11）。
- 不足：版本号没有生成/校验机制，文档更新不在发布检查清单内。

## 6. 根因归纳

| 根因 | 说明 | 直接导致的偏差 |
| --- | --- | --- |
| R1 文本模型缺少「字面/语法」分层 | IR 只存字符串与 marks/links，S4 无转义层；源文本可直接成为 Markdown/HTML 语法 | D2、D3、D4（表格变体） |
| R2 结构判定依赖单特征/文本模式 | 标题只看字号，列表只看行首正则，缺少版面角色与 `w:numPr` 等强信号 | D2 列表分支、D7 |
| R3 有损结构缺少降维账本 | 分页只到段尾、嵌套表不计数、合并表只计 span/vMerge | D5、D6 |
| R4 出口契约不统一 | md 失败吞掉、结果行与产物不一致、limit=0 多义、PATCH 无 no-op | D1、D8、D9、D12 |
| R5 异常/配置边界未分类 | 配置 JSON 异常逃逸 E5000；日志字段直接切片 | D10、D13 |
| R6 测试以语料/黄金为主，缺少对抗性语义断言 | 语料未覆盖 Markdown 字面量、原始 HTML、段内分页、嵌套表；黄金只保证字节不变，不保证语义正确 | D2、D3、D4、D5、D6 |
| R7 版本文档无单一来源 | README 手工维护 | D11 |

R6 需要特别说明：全量 1208 条测试与 22 份语料全绿，并不代表语义正确。现有黄金样本主要锁定「既有输出字节」，而本轮 13 项偏差中有 5 项（D2/D3/D4/D5/D6）在既有语料中根本没有对应输入。**测试通过的边界，就是语料覆盖的边界**；这不是测试执行不认真，而是测试设计缺少「对抗性字面量/结构降维」这一类用例。

## 7. 与第一轮遗留项的关系

| 遗留项 | 本轮状态 | 说明 |
| --- | --- | --- |
| O-11 行内跨度级链接 | 仍延后（ADR） | 本轮 D2 暴露了「块级链接 + 未转义」的组合风险，建议在 O-11 前先做字面量转义 |
| O-12 legacy 内置解析器 | 仍延后 | 本轮 legacy `.doc` 经 LibreOffice 通过；无 LibreOffice 环境仍不可用 |
| PDF 标题真值 | 仍缺 | `heading_pr` 在 PDF 上显示 `—`；D7 说明没有真值就无法量化标题准确率 |
| N-5 RTL 阈值 | 未校准 | 本轮未构造 W1046 夹具；与 D7 同属「单阈值缺校准」问题 |
| 安全/权限覆盖 | 不足 | `security/perms.py` 语句覆盖 38%；本轮的 RBAC 只覆盖 reader 提交任务一条越权路径 |

## 8. 影响排序

按「语义破坏 × 触发概率 × 下游放大」排序：

1. **D3**：原始 HTML/`javascript:` 直通；一旦下游渲染，安全影响最高。
2. **D2**：字面 Markdown 被解释；任何包含 `#`、`>`、`[]()`、`**`、`1.` 的正文都会触发，概率高。
3. **D7**：标题假阳性；影响结构、TOC、检索分块，概率中等。
4. **D4**：表格列错位；含反斜杠+管道的单元格触发，概率低但结果确定性错误。
5. **D1**：失败报成功；触发条件是落盘失败，概率低，但会破坏自动化决策。
6. **D8/D9/D10/D12/D13/D11/D5/D6**：边界/契约/可观测性，单独影响有限，但会累积成维护成本与误判。

下一步的可落地改造见 `docs/qa/round2/optimization-plan.md`。
