## 2. P0 改进项

### P0-1 建立「字面量转义 + 安全净化」层（D2、D3）

**问题回顾**

- `s4_render._inline` 只包 marks/links，不转义正文（`doc2md/pipeline/s4_render.py:120-141`）。
- 块级前缀由文本内容直接决定：`#` 变标题、`>` 变引用、`1.` 变列表；`[x](url)` 变链接；`<script>`/`<img onerror>` 原样输出。
- 表格单元格的 `<br>` 同时承担「结构换行」与「源字面」两种含义。

**调整策略**

1. **IR 增加文本模式**：为 `Block` 增加 `text_mode: literal|markdown`（默认 `literal`），或等价的 `escaped` 标志；LLM 修复产出的文本必须显式声明模式，不能默认信任。
2. **S4 两阶段渲染**：
   - 阶段 A：对 `literal` 文本做完整转义（行首块标记、行内 `* _ [ ] < > \`、有序列表前缀、HTML 标签），保留换行语义；
   - 阶段 B：按 `marks`/`links` 包装已转义的标签文本，块级前缀由渲染器生成而不是由正文内容决定。
3. **安全净化**：
   - 原始 HTML 一律转义为 `&lt;...&gt;`（或按配置白名单放行，但默认拒绝）；
   - 链接只允许 `http/https/mailto/ftp`；字面 `[x](javascript:...)` 不进入链接语法；
   - 表格单元格先转义字面 `<`/`>`，再用受控哨兵（如 `\x00BR\x00`）表示结构换行，最后统一替换为 `<br>`，避免歧义。
4. **S4.5 后渲染校验**：对输出做结构检查——正文块中不得出现未转义的行首 `#`/`>`/`1.`，不得含 `<script`/`onerror=`/`javascript:`，表格每行列数与表头一致；失败时抛 E5031 或标记 `render_contract_violation`，不得静默通过。

**预期效果**

- `md_literals.docx` 六段全部保持段落语义，不新增 H1/引用/链接/粗体/列表；
- `html_probe.docx` 输出中 `<script>`、`<img onerror>` 被转义，`javascript:` 不成为链接；
- P0-1 关闭 D2/D3，P0 用例通过率从 89.66% 提升到 96.55%（28/29）；余下 D7 由 P0-2 关闭后达到 100%。

**涉及模块**

`doc2md/ir/model.py`、`doc2md/pipeline/s3_structure.py`、`doc2md/pipeline/s4_render.py`、`doc2md/pipeline/convert.py`、`doc2md/llm.py`、`doc2md/pipeline/batch.py`。

**回归验证**

- 新增对抗语料：`md_literals.docx`、`html_probe.docx`、含字面 `<br>` 的表格、含 `\|` 的表格；
- 断言：渲染后字面文本逐字一致；无原始 HTML；表格列数不变；P0 用例全绿；
- 全量套件 + 22 份语料 + 黄金样本；对既有输出做 diff，确认变更仅来自字面量转义；
- 建议引入 dev-only Markdown 解析器（`markdown-it-py`）做结构回读，避免只做字符串断言。

**风险与取舍**

- **输出变更面大**：所有含 Markdown 元字符的文档都会变化，属于行为级变更；应按 minor 版本发布并在 release notes 明示「字面量不再被解释为语法」。
- **过度转义**：代码块、链接标签、表格分隔行不能套用同一规则；必须在「叶子文本」层转义，渲染器生成的结构标记不转义。
- **下游兼容**：依赖「源文本直接变成 Markdown 链接」的用户会受影响；这是安全修复的必要代价，不提供关闭默认转义的开关，最多提供显式的 `text_mode=markdown` 由调用方承担风险。
- **性能**：逐字符扫描增加 O(n) 开销，预计对 320p（59 万字符）增加 <5% 时延；需在 P2-3 基准中复核。

### P0-2 标题判定改为多信号 + 置信度（D7）

**问题回顾**

- N-8 无编号分支只看 `size >= base+3.5`、长度、句末标点（`doc2md/pipeline/s3_structure.py:1044-1047`），14pt 提示框被升为 H2。
- 真实标题与提示框可能同字号，单阈值无法区分。

**调整策略**

1. **信号集**：字号差、粗体、居中/左对齐、段前/段后间距、是否独立成行、是否在框线/底色容器内、是否带编号、是否位于页首/节首、前后文是否连续句子。
2. **DOCX 优先元数据**：有 `w:pStyle`（Heading 1–6）时直接采信；有 `w:numPr` 时优先按列表处理，不再走标题正则。
3. **判定器返回置信度**：高置信直接定级；中置信要求至少两个独立信号；低置信保持段落。N-8 的「大字号无编号」只在「独立成行 + 非容器内 + 前后有空白」时启用。
4. **提示框/标注识别**：检测 `w:drawing`/文本框、底纹、边框、居中短行等容器特征，命中时禁止升标题。
5. **真值评估**：建立人工标注的标题/提示框集合（DOCX 用样式真值，PDF 用人工标注），输出 precision/recall/F1；不再用「语料字节不变」代替准确率。

**预期效果**

- 14pt 提示框保持段落；`big_subtitle.pdf` 的 H1 仍为 H1；
- 标题 precision 在真值集上 ≥95%，recall 不低于当前基线；
- D7 关闭后补回最后一个 P0 失败项（3.45 个百分点），P0 通过率达到 29/29 = 100%。

**涉及模块**

`pipeline/s1_parse.py`（样式/容器特征）、`pipeline/s3_structure.py`（判定器）、`qa_eval.py`（指标）、`tests/`（真值集）。

**回归验证**

- `big_subtitle.pdf` 断言提示框为 paragraph；
- 语料 `pdf_04`/`pdf_07` 的「代码说明」「结语」不被漏判；
- 真值集混淆矩阵：标题 precision/recall/F1；提示框误判数为 0；
- 全量套件 + 黄金样本；重点检查 `docx_08_large_30sections` 的 270 块结构。

**风险与取舍**

- **召回下降**：多信号会漏掉一些只有字号信号的标题；用置信度分层和真值集调参，不用单一阈值硬扛。
- **PDF 几何依赖**：不同生成器的间距/对齐噪声大；需要按生成器分组评估，避免在一个样本上过拟合。
- **DOCX 样式缺失**：手排 Word 文档没有 Heading 样式，仍需启发式兜底；此时应降级为「中置信」而不是直接升 H2。
- **工作量**：需要标注真值集，短期成本高于调阈值；但这是唯一能避免「调一个阈值、坏另一个样本」的路径。

## 3. P1 改进项

### P1-1 表格单元格编码器与降维账本（D4、D5）

**问题回顾**

- `_gfm_table` 用链式 `replace` 处理 `|`，未处理反斜杠奇偶与字面 `<br>`（`s3_structure.py:481-497`）。
- 嵌套表拍平不计入 `flat`，W1045 不触发（`s1_parse.py:1033-1112`）。

**调整策略**

1. 写一个**有状态单元格编码器**：按字符扫描，先转义反斜杠，再转义管道/换行/HTML；结构换行用哨兵，最后统一替换。
2. `_docx_table_rows` 增加 `nested_tables` 计数；`_docx_cell_text` 遇到 `w:tbl` 时递增并上报；S3 汇总到 `flattened_cells` 或新增 `nested_flattened`。
3. W1045 的 message/detail 区分 `merged_cells` 与 `nested_tables`，避免把所有降维混为一谈。
4. 列数校验：输出前断言每行单元格数一致；不一致时补齐并记录 `table_row_mismatch`（新增告警或复用 W1045）。

**预期效果**

- `反斜杠\|组合` 在 GFM 中仍是一个单元格，渲染文本为 `反斜杠\|组合`；
- 嵌套表拍平 100% 触发 W1045；
- 复杂表列数稳定，D4/D5 关闭。

**涉及模块**：`pipeline/s1_parse.py`、`pipeline/s3_structure.py`、`pipeline/convert.py`、`errors.py`。

**回归验证**

- 新增表格夹具：字面 `\|`、字面 `<br>`、嵌套表、合并表、超宽表；
- 断言：列数不变、单元格文本 round-trip、W1045 计数正确；
- 语料 `docx_03`/`docx_11` + 全量套件；对既有表格输出做 diff，确认仅转义相关变化。

**风险与取舍**

- GFM 不支持合并/嵌套，降维不可避免；本项只保证「降维可见、内容不串列」，不承诺保留合并语义。
- W1045 可能变多，报告页需要聚合展示，避免告警噪声。
- 表格编码器改变既有输出字节，需纳入黄金样本更新审查。

### P1-2 段内分页按 run 位置切分（D6）

**问题回顾**

- `read_docx` 在整段处理完后追加 `\x0c` 行（`s1_parse.py:1178-1182`），段内分页前后文已合并。

**调整策略**

1. 解析段落时按 run 遍历，遇到 `w:br type="page"` 就切分当前 `Line`：前半段成行、插入 `page_break` 信号、后半段继续累积。
2. 为切分后的行保留 `page`、`source_run`、`paragraph_index` 等 provenance，便于审计与块 ID 稳定。
3. S3 仍按现有 `\x0c` 信号生成 `page_break`，但位置由 run 决定；若段内还有多个分页，按序切多段。

**预期效果**

- `pagebreak_in_para.docx` 输出「前段 / page_break / 后段」三段；
- 分页位置在 IR 与审阅页可验证；D6 关闭。

**涉及模块**：`pipeline/s1_parse.py`、`pipeline/s3_structure.py`、`ir/model.py`。

**回归验证**

- 新增段内单分页/多分页夹具；
- 断言块序、每段文本、`page_break` 数量；
- 全量套件 + 语料 `docx_05`/`docx_08`；检查块 ID 变化是否影响编辑锁。

**风险与取舍**

- 切分会改变块数与块 ID，已有用户编辑的 `doc_id + block_id` 映射可能失效；需要在重转冲突（E4091）路径中明确提示，不能静默覆盖。
- 分页符在表格/文本框内的语义复杂，先支持正文段落，容器内保持现状并记录告警。

### P1-3 统一 CLI/API 出口契约（D1、D8、D9、D12）

**问题回顾**

- md 直出失败仍 rc0/status ok（D1）；
- 同值 PATCH 递增 revision（D8）；
- `limit=0` 三义（D9）；
- md 模式结果行报告已删除 zip（D12）。

**调整策略**

1. **统一结果对象**：CLI 每条结果包含 `status`（ok/failed/skipped/rejected）、`artifacts`（实际存在/已删除）、`error`（code/message）、`warnings`；rc 由最严重状态推导，不允许 stderr 有错误而 stdout ok。
2. **格式出口失败回写**：`_apply_format` 返回 `FormatResult`（path/error），失败时把结果状态改为 `failed`、code E5031、rc 4；zip 保留，便于重试。
3. **PATCH no-op**：读取 `old_text` 后先比较；相同则返回 `revision` 不变、`unchanged=true`，不写审计、不递增。若调用方需要「强制写」，提供显式 `force=true`。
4. **limit 语义统一**：选择「显式 0 = 空集」作为统一契约；缺省参数才使用端点默认值。在 `_window`、`/jobs`、`/search`、`list_docs` 共用同一解析函数；CLI 与 HTTP 共用。
5. **结果行产物一致性**：md 模式删除 zip 后，结果行省略 `zip` 或输出 `zip_removed=true`；不要保留一个指向不存在文件的路径。

**预期效果**

- 所有失败路径 rc/status 可被机器判定；
- 同值 PATCH 不再制造假冲突；
- 四个列表/检索出口对 0 的行为一致；
- 结果行与磁盘事实一致；D1/D8/D9/D12 关闭。

**涉及模块**：`cli.py`、`api.py`、`edits.py`、`storage/repo.py`、`pipeline/batch.py`。

**回归验证**

- CLI：目录占位导致 md 失败 → rc4/E5031；md 模式结果行无 zip 或标 `zip_removed`；
- API：同值 PATCH → revision 不变、审计不增；过期 revision → E4251；四出口 `limit=0` 参数化测试；
- 批处理：失败行与成功行 rc 聚合仍正确；
- 全量套件中的 CLI/API 测试。

**风险与取舍**

- 结果行字段变化会影响外部脚本；建议保留旧字段但新增 `status=failed`/`artifacts`，并在 release notes 标注。
- `limit=0` 选「空集」会让依赖「0=默认」的调用方行为变化；这是消除歧义的必要选择，需在 API 文档写清。
- 同值 PATCH 不递增 revision 会改变乐观锁语义；需要明确的 `unchanged` 返回，避免客户端误以为写入失败。

### P1-4 配置错误映射为 E4001（D10）

**问题回顾**

- `create_app` 直接 `json.loads(override)`（`api.py:151-157`），JSON 语法错误逃逸为 E5000/rc5。

**调整策略**

1. 在配置加载边界捕获 `JSONDecodeError`/`OSError`，抛 E4001，detail 带文件路径、行列号；
2. CLI 顶层保留 E5000 作为真正的内部错误兜底；
3. `settings GET/PUT` 与启动路径共用同一套 override 解析器，避免两处行为不一致。

**预期效果**

- 损坏 override → rc2、E4001、可定位；D10 关闭。

**涉及模块**：`api.py`、`config/loader.py`、`cli.py`。

**回归验证**

- `badsettings` 夹具启动 → rc2/E4001；
- 合法 override 仍正常；
- `settings PUT` 写入非法 JSON 的路径也返回 E4001。

**风险与取舍**：低；主要是错误码变化，调用方从「内部错误」改为「配置错误」，属于契约修正。

### P1-5 告警与错误码覆盖补齐（覆盖缺口）

**调整策略**

1. 新增夹具：跨片表格（W1043）、旋转页/RTL（W1046）、过期 `base_revision`（E4251）、超大文件（E4131）、超宽目录（E4133）、不可消毒文件名（E4003）、同路径并发替换（E4092）。
2. 将 W1043/W1046 的触发条件写成参数化测试，断言 warnings 与报告页展示。
3. 在 QA 文档中把错误码覆盖率从 9/14 提升到 ≥12/14；E4003/E4092 需平台/资源条件，登记为环境限制而不是「已覆盖」。

**预期效果**：告警 4/4、错误码 ≥12/14；分片/RTL/并发路径有可复现证据。

**涉及模块**：`pipeline/sharding.py`、`s1_parse.py`、`api.py`、`tests/`。

**风险与取舍**：构造超宽目录/超大文件会占用磁盘与时间，需在临时目录、限额内执行；W1046 的 RTL 判定阈值未校准，先验证「能触发」再谈准确率。

## 4. P2 改进项

### P2-1 work 日志路径可定位（D13）

- 改为记录完整路径；如担心日志体积/敏感信息，记录 `basename + sha256(path)[:16] + 目录`，并提供 `--log-full-path` 开关。
- 预期：任意 `job_done` 可按日志定位源文件；D13 关闭。
- 模块：`worker.py`、`ops/logging.py`。
- 回归：长路径（>64 字符）与短路径各一条；确认无正文泄漏。
- 风险：完整路径可能含用户名/项目名，需在隐私要求高的部署中默认哈希；这是一项配置取舍。

### P2-2 版本单一来源（D11）

- README 版本从 `pyproject.toml` 生成或由测试校验；CI 增加 `test_readme_version_matches_pyproject`。
- 预期：三处版本一致；D11 关闭。
- 模块：`README.md`、`pyproject.toml`、`tests/`。
- 风险：低；生成式文档需要在发布流程中执行，否则仍会漂移。

### P2-3 性能与平台口径（235MB 附注）

- 在文档中区分 macOS/Linux 的 RSS 参考值；把四档基准纳入可选 CI（或定时任务），记录 P50/P95。
- 目标：320p ≤10.5 s、RSS ≤250 MB；P0-1 转义层上线后复核是否回退。
- 模块：`tests/perf/`、`docs/`。
- 风险：CI 机器差异会导致阈值噪声；只做趋势告警，不做硬门禁，硬门禁保留在本机基线。

### P2-4 长期能力补齐

| 项 | 内容 | 说明 |
| --- | --- | --- |
| O-11 行内跨度链接 | span 级链接模型 + 多链接渲染 | 当前块级模型会丢多链接；与 P0-1 的转义层一起设计，避免重复改动 |
| O-12 legacy 内置解析器 | 无 LibreOffice 环境的 `.doc` 解析 | 当前依赖外部二进制；需评估维护成本与格式覆盖 |
| PDF 标题真值 | 人工标注标题/提示框集合 | D7 的量化前提；没有真值就无法判断 precision/recall |
| N-5 RTL 校准 | 用真实 RTL 文档校准 W1046 阈值 | 当前只探测不修复；阈值未校准会漏报/误报 |
| 安全/权限覆盖 | `security/perms.py` 从 38% 提升到 ≥80% | 目录权限矩阵的异常分支需要端到端测试 |

## 7. 总体风险与取舍

1. **输出兼容性**：P0-1 会改变含 Markdown 元字符文档的输出，属于行为级变更；应作为 minor 版本发布，提供迁移说明，不提供「关闭转义」的默认开关。
2. **标题召回/精度权衡**：P0-2 可能降低少数真实标题的召回；以真值集为准，不用单个语料调参。
3. **块 ID 稳定性**：P1-2 分页切分会改变块数/ID，影响已有编辑；需要在重转冲突路径明确提示，必要时提供一次性迁移工具。
4. **契约变化**：P1-3 的 `limit=0` 与 PATCH no-op 会改变客户端可观察行为；需要在 API 文档与 release notes 中同步，并保留一个过渡期的兼容字段。
5. **测试依赖**：结构回读如果引入 Markdown 解析器，会增加 dev 依赖；建议仅测试环境使用，生产零依赖不变。
6. **性能回退**：转义与表格扫描是 O(n)，预计影响 <5%；若超过阈值，优先优化扫描器，不放宽安全规则。
7. **不做的取舍**：本轮不建议为了 D7 简单调高 N-8 阈值，也不建议为 D4 只加一条 `replace("\\\\","\\\\\\\\")`——两者都会把问题推到下一个样本；必须按上面的结构化方案修复。

## 8. 结论

- 这 13 项偏差中，**2 项高、3 项中、8 项低/中低**；但高项都集中在「文本即 Markdown」这一条根因上，修复收益远大于逐条打补丁。
- 建议以 P0-1 为第一优先，P0-2 紧随其后；P1-3 的出口契约修复成本低，可与 P0 并行。
- 只要 P0 两项与 P1-1/P1-3 完成，预计 P0 通过率可达 100%，总体通过率可到 90% 以上；剩余低等级项按 P2 收尾。
