## 2. P0 改进项（全部受限，本轮只登记）

### OPT4-1 S1 行装配几何化：跨页表整列脱落 + 裂表（D-2 / B-43）

- **根因**：R7 + R8。`doc2md/pipeline/s1_parse.py` 的 PDF 侧行装配信任 pdfminer 的**文本流顺序**，而不是按 **y 坐标聚类**。跨页续表的第 2 页残余因此成为独立表（表头重复），而 `金额` 列在流序里与主体脱开，整体脱落成正文一长串 `金额10011002…1036`。
- **调整策略**：
  1. 行装配改为「先按 y 带聚类成行、再在行内按 x 间隙聚类成列」两步，两步各自独立可测；y 带高度取该页字符高度中位数，容忍 ±20% 漂移（基线与容差必须由真实文档量出，不能拍）。
  2. 跨页续表合并判据：下一页首个行组若**列数与上一表一致且列 x 区间重合度 ≥ 阈值**，则并入上一表而不另起；阈值同样需实测量出。
  3. **降维入账范围扩到列脱落**：`W1045` 当前只在合并单元格拍平时触发，必须覆盖「列归属丢失」「裂表后合并」两种形态，否则修对了也没有可观测性（R8）。
- **预期效果**：D02 由 `2 列 × 37 行 + 3 列 × 5 行` 变为 `3 列 × ≥41 行` 单表；`table 多余: 2 > 1` 消失；列脱落时 `warnings` 至少 1 条。
- **涉及模块**：`pipeline/s1_parse.py`（PDF 行/列装配）、`pipeline/s3_structure.py`（表格分组与续表合并）、`ir/__init__.py`（若 `W1045` 语义扩面需改 `detail` 形态）、`tests/corpus/expected/*.md`（黄金重烤）。
- **回归验证方式**：
  - `tests/corpus/run_hard.py` D02 由 FAIL 转 PASS，其余 9 条不得转红；
  - `tests/qa/test_hard_gate.py::test_hard_expectations_structure[D02]` 的 `xfail(strict)` 转 **XPASS**（strict 会先转红提醒，这是设计好的信号）；
  - `.venv/bin/python tests/corpus/run_corpus.py` 22/22 逐字节；
  - `.venv/bin/python tests/corpus/run_metrics.py` 表格列一致率各批 macro 保持 1.0、漂移 F1 保持 1.0；
  - `.venv/bin/python -m tests.qa.evaluate` 的 `table_teds`（现 0.9874）与 `table_shape_ok`（现 1.0）不得下降；
  - `.venv/bin/python ops/bench/opt6_shard_equivalence.py` exit 0（320 页金样本五面等价，正文 1775484 B / 5789 块）；
  - 门禁与全量套件 0 failed，覆盖率不得低于精确 90.60%；
  - `PIPELINE_VERSION` 契约级升位，与黄金重烤同批。
- **风险与取舍**：
  - **最大风险是「修对 D02、修坏 22 篇」**。几何化改的是最底层的行装配，所有 PDF 路径都经过它。缓解：分两步提交，第一步只做「y 带聚类」且要求 22 篇逐字节不变（这一步应当是无损重构），第二步才做续表合并（这一步必然改字节，与重烤同批）。
  - **`pdf_10_two_column_6p` 是唯一的双栏 oracle**，几何化改坏双栏很难被发现。缓解：先补双栏语料（见 OPT4-4 的同型做法），再动几何化。
  - 取舍：`B-39`（绕过 pdfplumber 的 per-object 展开）与本项**必须排序**——先做本项（改判据，不换后端），B-39 押后（换后端，等价面极宽）。
- **受限原因**：「正确列归属」要人工逐页对照真实 PDF 才敢定——本机 22 篇语料全是生成器写的，几何形态规整，无法暴露真实文档的容差边界。
- **验证方式（人工侧）**：取 ≥5 篇真实含跨页表的 PDF，逐页人工标注列归属与行数，与产物对照；容差与阈值从标注结果反推。
- **建议执行顺序**：**发布前第 1 位**（与 OPT4-2 同批，见下）。

### OPT4-2 目录形态识别与降级告警 + 单元格空格保真（D-3 / B-44）

**本项必须拆成两半分别处置**——两半的受限性不同。

#### 2a. 空格保真半（**本机可做，但需与黄金重烤同批**）

- **根因**：`doc2md/pipeline/s1_parse.py::_row_cells` 两处叠加：入口 `cs = [c for c in chars if (c.get("text") or "").strip()]` 把纯空白字符**整颗丢掉**；出口 `return ["".join(seg).strip() for seg in cells]` **无分隔符**连接。于是 `第一章 总则` 塌成 `第一章总则`。
- **实测影响面**：220 行 PDF 表格行中 **17 行**受影响（`hard_05_leader_dots`、`hard_08_header_variants` 8 行、`pdf_10_two_column_6p` 6 行）。
- **加重情节**：DOCX 路径的单元格文本**保留**空格，只有 PDF 路径删——同一语义两条实现产出两种字节（格式不一致）。
- **调整策略**：入口过滤保留空白字符参与聚类（只在**判断是否成行**时忽略空白，不在**拼装**时丢弃）；出口按相邻字符的 x 间隙决定是否插入一个空格（间隙 > 0.6 × 字宽中位数即插空格），而不是无条件 `"".join`。这样既不塌词，也不会把每个字符间都塞空格。
- **预期效果**：`第一章 总则` 原样保真；`contains` 三条由全缺转为命中；PDF 与 DOCX 两条路径的单元格空格语义一致。
- **涉及模块**：`pipeline/s1_parse.py::_row_cells`、`tests/corpus/expected/*.md`（重烤）。
- **回归验证方式**：`run_hard.py` D05 的 `contains` 三条转 PASS；`run_corpus.py` 22/22（**重烤后**）；`defect_scan` 的 `cjk_space_collapse` 规则保持 0 命中；`run_metrics.py` 表格列一致率保持 1.0；门禁/全量 0 failed。
- **风险与取舍**：改的是**所有 PDF 表格单元格**的字节，重烤面最宽。缓解：先在 `pdf_10_two_column_6p`（6 行受影响）与 `hard_08_header_variants`（8 行）上出 diff，逐行人工确认「只有空格回来了、没有别的字符变化」，再全量重烤。**依赖 OPT4-8 的 diff 报告能力**，否则人工复核成本过高。
- **为什么至今未做**：不是难度，是**产物字节冻结税**（R9）——改法明确、不需人工裁定，但必须与重烤同批。

#### 2b. 目录形态识别半（**受限**）

- **根因**：R6——三个各自合理的局部规则叠加产生全局损伤，且**没有任何一层看得见这个叠加**：① `_row_cells` 的间隙聚类把整页目录判成表格；② `doc2md/pipeline/s3_structure.py::analyze` 主循环的 `if ln.row: lvl = None`（CH-485 / R9-PIPE-4，本意是不让表格首列的 `1.1 范围` 被当成多级编号标题）封锁标题晋升；③ 空白字符不入聚类导致塌词。三者叠加后，`第一章 总则` 既不成标题、又字面失真。
- **调整策略**：在 S3 增「目录形态」识别——判据候选：引导符密度（`.` / `…` 连续占比）、页码右对齐、行结构同质度、整页行数。命中后**不成表**，改按「章节名 + 页码」的列表形态交付，并立**新 W 码**（附录 D 预留位 W1047–W1051 之一）入账「本页按目录形态降级」。
- **预期效果**：D05 整页不再被判成表格；`| 第一章总则 | .... | 1 |` 形态消失；降级留告警。
- **涉及模块**：`pipeline/s3_structure.py`（目录形态识别 + 降级分支）、`ir/__init__.py`（新 W 码常量）、`docs/dev-plan.md` 附录 D（预留位转正）、`tests/qa/trace.py`（W 覆盖率分母由 4 变 5）。
- **回归验证方式**：`run_hard.py` D05 转 PASS；**D01（无线框表格）必须同时保持 PASS**——D01 要求「无边框也成表」、D05 要求「无边框的目录不成表」，同一几何特征两侧要一起调，**只修一边会把另一条样本推红**；`trace.py` 的 W 覆盖率保持 1.0（分母 5）；门禁/全量 0 failed。
- **风险与取舍**：目录识别是**误判面最宽**的一类启发式——真实文档里「点线 + 右对齐页码」也可能出现在价目表、索引表、签收单里。误判成目录会把真表格降维成列表，比现状更糟。这就是必须先有人工阈值确认的原因。
- **受限原因**：阈值（引导符密度 / 页码右对齐 / 行数）需人工在**真实目录页**上确认可误判面；本机 31 份夹具里只有 `hard_05_leader_dots` 一份是目录形态，样本量不足以定阈值。
- **验证方式（人工侧）**：取 ≥10 篇真实文档的目录页 + ≥10 篇含点线/右对齐页码的**非目录页**（价目表、索引、签收单），人工标注两侧，反推阈值并给出误判率。
- **建议执行顺序**：**发布前第 1 位，与 OPT4-1 同批**（两者都动 S1/S3 的表格判据，分开做会互相推红）。

### OPT4-4 补「LibreOffice 写出的 DOCX」语料形状（R1，**本机可做 · 本轮最高性价比**）

- **为什么排 P1 首位**：D-1（R19-PIPE-3）躲过了门禁 679 项 / 全量 1512 项 / 语料 22/22 / `ideal` 21 篇**全部四条既有腿**，唯一原因是 22 篇语料的 DOCX 都由 python-docx 写出，编号形态单一。**再加十条 python-docx 语料也抓不到同类缺陷**；补一种文档形状比补十条同形状语料有效得多。
- **调整策略**：在 `tests/corpus/make_corpus.py` 增一组「LibreOffice 形状」DOCX 语料（生成后用本机 `soffice --convert-to docx` 过一遍，或直接按该形状构造 XML），至少覆盖三形态：
  1. 标题样式挂**样式级** `w:pPr/w:numPr → numId=1`，而 `numId=1 → abstractNumId=1` 的级别是 `numFmt="none"` + 空 `lvlText`（D-1 的命中形态）；
  2. 段落级 `numPr` 指向 `numFmt="bullet"` + 非空 `lvlText`（正向守卫，不得回归）；

### OPT4-5 附录 C 契约表与实测响应体自动对账（R2 / C-1..C-6，**本机可做**）

### OPT4-10 探针前提回读 + 「不得出现」型红线强制配正夹具（R3 / R4，**本机可做**）

- **根因**：本轮八项观察项里，**O-c / O-d / O-e / O-g / O-h 五项是同一个根因**——断言或引用的前提来自记忆和直觉，而不是回读文件。O-b 是另一形态：红线的前件恒假，断言恒真，无论产品怎么改都 PASS（第三轮 O-g 同型再现，说明该根因**没有随上一轮登记而消失**）。
- **调整策略**：
  1. **纪律条文化**（写进 `docs/dev-plan.md` 的 QA 章）：① 探针断言里的每一个常量（元素 id、字段名、错误码、状态码）必须**从源文件实测取值**，不得凭记忆写；② 凡「某物不得出现」型红线，**必须配一条正夹具**证明「同一检查在应当命中的地方确实命中」；③ 引用扫描器命中数前必须回读它的**已知良性登记表**；④ 登记缺口前必须先读注册表尾部，**同题并入、新题才开号**。
  2. **正夹具形态可推广**（TC-M8-04 改后的样子）：交付面命中数必须为 0，**且** `ir.json` 命中数必须 > 0（实测 `delivery_hits={'content.md':0,'report.html':0}`、`ir_json_hits=1120`）。后一个数不是断言目标，是「这条断言确实有牙齿」的证据。
  3. **存量排查**：对 `tests/` 里所有「不得出现」型断言做一次扫描，逐条确认是否有正夹具。这一步本机可做，产出是一张清单，不是一次性改完。
- **预期效果**：恒真红线不再可能长期存活；探针首跑失败时能立即区分「产品错了」与「断言错了」（本轮 O-a / O-d / O-e 三例都是断言错，各花了一轮复核才确认）。
- **涉及模块**：`docs/dev-plan.md`（纪律条文）、`tests/`（存量排查清单，不批量改）。

- **调整策略**：按 B-11 既有登记，人工在真实浏览器（Chromium / Chrome / Safari 各一次，Windows 与 macOS 各一遍）走查四链路：加载 → 编辑保存 → 冲突提示 → 回滚 → 审计显示。
- **预期效果**：R19-GUI-1..4 四项修复从「源码静态断言把守」升级为「实机走查确认」。
- **涉及模块**：`static/editor.html`、`api.py::index`。
- **回归验证方式**：走查记录留痕（B-11 的 CH-496/CH-498 两轮已有同型记录可照格式）；控制台消息数必须为 0；网络面只出现预期端点。

- **受限原因**：本机无浏览器自动化 harness；webview 侧键盘事件与 AX 行为另有已知限制。
- **建议执行顺序**：受限项第 9 位。**并入既有 B-11，不新开编号**（O-g 纪律）。

### OPT4-22 真实样本腿（B-49，**受限**）

- **现状**：`tests/corpus/real/run_real.py` 已落地并自证——无样本时记 `not_run` + 原因、退 0、写出「未执行」占位工作表（**不冒充 pass**）。本机 `work/real_samples` 为空，故该腿恒 `not_run`，`tests/qa/realtest.py` 报 `NOTRUN=2`（另一条是 `L4_install/clean_venv_install`）。**这是诚实状态，不是缺陷。**
- **调整策略**：人工把 ≥5 篇真实 Word / PDF 放进 `work/real_samples/`（gitignored；**不要放进 `tests/`**，隐私红线会拦），逐篇在 `tests/corpus/real/ground_truth.json` 标注标题真值，跑 `.venv/bin/python tests/corpus/real/run_real.py --sample 5 --repeats 2`，再把 `work/qa/real_sampling.md` 的人工两栏填完。

- **涉及模块**：`tests/corpus/real/`、`work/`（gitignored）。
- **回归验证方式**：如上；`recall` 偏低时先核对标注是否覆盖该篇（`gt=` 那个数就是「有人工真值的篇数」）。
- **受限原因**：本机无真实用户样本；且真实样本涉及隐私，不能入库。
- **建议执行顺序**：受限项第 10 位。**与 OPT4-20 可合并**（同一批人工标注动作）。

## 7. 总体风险与取舍

### 7.1 最大的风险：本机可做项无法解除发布阻断

九项本机可做（OPT4-4/5/8/10/11/12/16/17/19）全部落地后，`release_blocking` **仍然是 `['B-43','B-44']`**。这不是排期失误，是**缺陷分布的客观结果**：两项发布阻断缺陷的根因（R6 局部规则叠加、R7 几何信息在装配前被丢弃）都需要**真实文档的人工对照**才能定阈值——本机 22 篇语料全是生成器写的，几何形态规整，无法暴露真实文档的容差边界。

**取舍**：与其把人力投在「让本机可做项更快落地」，不如**先安排受限项里的人工动作**（OPT4-1/2 的逐页对照、OPT4-20/22 的标注）。本机可做项的价值在于**提高下一轮的可见性**（OPT4-4）、**降低后续施工成本**（OPT4-8）、**防止同类缺陷再潜伏**（OPT4-5/10/12/19），不在于解除当前阻断。

### 7.2 第二个风险：产物字节冻结税会持续挡住「改法已知」的修复

OPT4-2a（空格保真）与 OPT4-16（转义单一来源）都是**改法明确、不需人工裁定**的项，长期停在登记状态的唯一原因是重烤需人工逐篇复核。OPT4-8 是针对这一点的**元改进**——它不修任何产品缺陷，但把后续每一项字节级修复的人工成本从「读 22 篇产物」降到「读 X 条结构变化」。

**取舍**：OPT4-8 应当**早做**。它排在第 3 位而不是更后，正是因为 OPT4-2a / OPT4-16 / OPT4-17 三项都在等它。

### 7.3 第三个风险：真值面的自证循环

`ideal/` 21 份标注是程序化真值，`expected/` 22 篇是重烤基线（只防漂移、不判对错）。**唯一的独立真值面是 `tests/corpus/hard/`（10 篇，6/10）与尚未投入的真实样本腿**。这意味着：

- 标题 F1=1.0 **不能**证明标题判得对，只能证明与程序化标注一致；
- 语料 22/22 **不能**证明转换正确，只能证明没有漂移；
- 门禁 683 全绿 **不能**证明无缺陷——D-1 就是在 679 项全绿的状态下存在的。

**取舍**：OPT4-4（补文档形状）与 OPT4-20/22（补人工真值）是**同一件事的两个方向**——前者扩形状覆盖（本机可做），后者扩真值独立性（需人工）。**两者都做才够**：只做前者，新形状仍用程序化真值；只做后者，人工标注只覆盖既有形状。

### 7.4 明确不做的事

- **不做破坏性重构**。B-30（散装 SQL 仓储化）、B-31（`s1_parse.py` / `cli.py` / `api.py` 三巨头拆分）维持登记：拆分时机必须与产物字节冻结**同批**做，否则等价性门无法区分「搬家」与「改行为」。本轮不安排。
- **不换 PDF 抽取后端**。B-39（绕过 pdfplumber 的 per-object 展开）押后于 OPT4-1：等价面极宽（旋转 / 连字 / CJK 宽度 / `/ToUnicode`），且收益次于 B-38。
- **不把 `run_hard.py` 的结果当门禁**。它退 1 是**诚实显形**，不得为了让收口好看而改成退 0；也不得把 `tests/qa/test_hard_corpus.py` 的骨架（只核对 `contains`/`not_contains`）当门禁——那会得出「难度语料无结构问题」的假结论（第三轮 O-g）。
- **不用 `skip` 掩盖平台差异**。Windows junction 的 2 条 skip 是**平台门**（本机无法执行），不是「跳过充抵通过」；跨 OS 的判定差异一律改进产品/测试口径，不加 `t.Skip`。

## 8. 结论

1. **本轮闭合一项高级别契约缺陷（D-1 / R19-PIPE-3）**，链路完整：根因 → 修复 → 4 项 gate 红线 → 三次变异证明 → 全量无回归（门禁 683/0、全量 1516/0、覆盖率 7843/737 = 精确 90.60%、语料 22/22、`ideal` 与 `evaluate` 指标逐项不变）。它是**通用 DOCX 缺陷**而非 `.doc` 专属，影响面覆盖所有 LibreOffice 写出的 DOCX。
2. **发布仍阻断**。D-2 / D-3 与第三轮同两条，B-43 / B-44 未闭合前不得发布，或由人工逐页对照真实 PDF 复核后出具书面豁免。`release_blocking = ['B-43','B-44']` 不变。
3. **22 项改进中本机可做 9 项、受限 13 项**。受限项按用户口径只登记不实施，逐条注明了受限原因、验证方式与建议执行顺序（第 2–4 节）。
4. **本轮最高性价比的投入是 OPT4-4**（补 LibreOffice 写出的 DOCX 语料形状）：它不修任何已知缺陷，但 D-1 之所以能躲过全部四条既有腿，正是因为语料里没有那个形状。**真值面的形状覆盖决定能看见什么缺陷**——这是本轮从 D-1 的定位过程里得到的、比 D-1 本身更有价值的结论。
5. **两项元改进应当优先**：OPT4-8（黄金重烤 diff 报告）解锁三项被字节冻结税挡住的修复；OPT4-5（附录 C 契约对账红线）让六项文档精度偏差在提交时即转红，而不是等下一轮 QA 人工发现。
6. **新增待办一项**：B-50（活文档行号引用棘轮，实测 173 处，只减不增）。**本册不新开其他编号**——TC-MG-09 并入既有 B-11（O-g 纪律：登记缺口前先读注册表尾部，同题并入、新题才开号）。
