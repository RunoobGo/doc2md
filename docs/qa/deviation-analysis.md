## 1. 解析环节（S1：PDF/DOCX/legacy → 页级行结构）

### 1.1 折行边界空白无几何证据（C-04，逻辑错误，中）

- 现象：pdf_09 中「数字 2026」在折线恰好落在该空格时丢空格（22 处中 1 处）。
- 根因：`extract_text_lines` 产出的 `Line.text` 剥掉了行首/行尾空白；S3 `_join_line`（`s3_structure.py:1008-1024`）对 CJK↔拉丁/数字边界统一按「无空格」拼接（`ord(last) > 0x2E80` 即 `return b`）。源文档中「此处有一个空格」的信息在 S1 被丢弃，S3 无从恢复。
- 性质：非规则错误，而是**信息缺失**——拼接规则对「源有空格」与「源无空格」两种情形给了同一个输出。

### 1.2 页眉剔除三条件对逐页变体失效（C-02，结构差异，低）

- 现象：pdf_10 的「第 N 页第 M 栏」逐页变化，未被 `_strip_page_furniture` 剔除。
- 根因：剔除判据是「同一边距行在 ≥2 页重复」（`_furniture_key` 归一化后计数）且满足字号/长度条件。逐页变化的栏标题 key 各不相同（计数恒 1），又不匹配 `_PAGE_NUM` 页码形态，故漏网。该函数的设计前提是「页眉页脚跨页稳定」，对逐页刷新的页眉（栏标题、奇偶页眉）无对策。

### 1.3 解析面已知边界（本轮未新增偏差，登记备查）

- legacy `.doc` 无内置解析器，转换能力取决于本机 LibreOffice/Word（C-35，兼容性，低）——架构选择（离线 + 零重型依赖）的必然代价，非缺陷。
- PDF 表格仅靠「行内字符横向间隙聚类」（`_row_cells`），不利用框线/单元格边框对象；无框线的宽列距表格存在漏判/误判面（套件有防误判守卫，本轮未触发）。

## 2. 映射环节（S3：行结构 → 七类块 IR）

### 2.1 IR 无列表容器，紧凑/松散语义无处安放（C-05，结构差异，中）

- 现象：所有连续 `list_item` 块之间输出空行（loose list）。
- 根因：`BLOCK_TYPES`（`ir/model.py:20`）只有条目级 `list_item`，没有「列表」容器；S3 逐项落块，S4 `render()` 对全部块类型统一 `"\n\n".join`。块模型不携带「这些项属于同一个紧凑列表」的分组信息，生成层就无法做出紧凑渲染。
- 加重因素：块间空行同时承担「段间分隔」职责，改动间距策略会影响段落语义，此前无需求驱动去拆。

### 2.2 GFM 表达力天花板未用回退兜底（C-06/07/10，结构差异，低）

- 现象：合并单元格拍平（「说明 数量」+ 空列）、单元格内多段落以单空格相连、脚注无行内锚点。
- 根因：三者都是**真实信息被迫降维**——GFM 表格无 colspan 语义（用空位对齐是 CH-483/R8-PIPE-5 的既定取舍）、单元格不能含裸换行（可用 `<br>` 但未用）、GFM 无脚注语法（不造 `[^1]` 死链是 FR-107 同口径的既定取舍）。属于「已知取舍」而非疏漏，但取舍结果对用户不可见（无显式提示），体验上等同于静默降级（与 C-29 同源）。

### 2.3 行内格式停留在块级（C-30，功能缺失，中）

- 现象：段内局部粗体/斜体（如一个词加粗）不进产物。
- 根因：`Block.marks` 是块级布尔；S1 只产 `uniform_*`（全行统一才置位，CH-483/R8-PIPE-7 的防扩散设计），IR 没有行内 span（区间 + 格式）模型。这是模型上限，不是 bug——但中文技术文档行内强调很常见，实际损失不小。

### 2.4 续段/标题启发式的边界脆弱性（潜在，本轮未触发偏差）

- `_continues_paragraph` / `_heading_level` 依赖「句末标点 + 首行缩进几何 + 字号差」组合信号。无首行缩进证据的版式（英文稿、诗歌体、右起排版）会退化为纯标点口径，段落切分粒度变粗。本轮语料未暴露，属潜在风险。

## 3. 生成环节（S4：IR → Markdown）

### 3.1 块间间距策略无类型感知（C-05 的生成侧根因）

- `render()`（`s4_render.py:57-70`）对所有非 code 块统一 `"\n\n"` 连接、统一压缩 `\n{3,}`。间距不感知「上块与本品是否同属一个列表/表格上下文」，是 C-05 的直接成因。
- 附带观察：空行压缩只跳过 code 块（CH-473 的正确设计），但「哪些块彼此紧邻」这一信息在 IR 里本来就不存在——又是 2.1 的模型问题在生成侧的投影。

### 3.2 输出字段一致性（C-21，低）

- 批量结果行 `sharded=None` vs 串行 `sharded=False`：批量路径（`pipeline/batch.py` 工人进程）与串行路径（`cli.py`）各自组装结果行，字段取值口径未对齐。纯一致性缺陷，不影响产物。

## 4. 校验环节（S1.5 门禁 / 语料基线 / 测试环境）

### 4.1 门禁只判「文本层密度」，不判「结构质量」（C-31 的根因之一）

- S1.5 判据是 chars/CJK 比/噪声比等**密度指标**；标题层级是否合理、表格列是否对齐、注文是否丢失这类**结构质量**没有任何自动判据。扫描件能拦（密度为零），但「结构烂但密度够」的文档会全须全尾地进入产物。

### 4.2 语料 expected 基线自啮合（C-31，校验口径，中）

- `run_corpus.py` 的 expected 由现行为 `--write-baseline` 生成后人工审阅（`make_corpus.py` 文件头自陈）。结果是：语料比对证明的是「现行为没有漂移」（防回归），**不能证明「现行为接近理想」**——C-04 的空格丢失、C-05 的松散列表都被基线原样吸收。没有 ground truth 标注语料（B-13/B-15 收样已完成、标注未完成，见方案 §5-9），「对理想」的判定只能靠人工语义核对（本册 C-01~C-14 即如此补齐）。

### 4.3 质量指标只有计数、没有对错（C-31 的根因之二）

- `_metrics()`（`convert.py:347-353`）只产 chars/headings/blocks/sharded 等计数，没有与源文档结构对照的准确率/召回率（标题 P/R、表格列一致率、字符级 F1）。没有量化质量曲线，「转换变好/变坏」不可度量，只能靠语料红绿二值。

### 4.4 测试环境未中立化（C-34，兼容性，中）

- 全量套件 9 项失败的根因：进程级 `HTTP_PROXY` 变量把回环测试流量导向外部代理（4 项 T2）、文件沙禁临时目录 `mkdir(EEXIST)`（2 项 ch476）与进程树采样（3 项 T6）。项目对「低配机口径」「沙箱 vs 真机」有严格纪律，却**没有把「代理变量清理 / 沙箱能力探测」做成 pytest 的 autouse 夹具**，导致每次环境差异都要人工归因（本轮即耗时于此）。CI 干净（无代理、无沙禁）所以从不暴露——这是「本机/沙箱 vs CI」两侧纪律不对称。
